# 保守清理无用代码设计

## 目标

在不改变网站现有页面、接口、样式、内容行为、第三方集成和公共接口的前提下，清理未使用的组件、代码、静态资源和 npm 依赖。

## 范围

本次清理包括：

- 没有消费者的 React 组件、Hook、Context、工具、服务和内部导出。
- 活跃文件中未使用的导入、变量、函数、类型，以及已废弃的注释代码。
- 未被源码、配置、元数据或文档引用，且不属于框架约定的静态资源。
- 没有被直接、间接使用，也不是框架或构建工具所必需的 npm 依赖和开发依赖。
- 能够证明不可达的代码分支，或与活跃实现重复且不提供独立行为的本地代码。

本次清理不包括：

- 删除或重新设计功能。
- 修改页面布局、文案、样式、URL、API 契约、SEO 输出或第三方集成行为。
- 调整目录结构、大范围合并组件或架构重构。
- 修改环境配置、部署配置、CI、数据库或迁移。
- 升级依赖。

## 安全规则

即使普通导入分析找不到消费者，也默认保留 Next.js 按约定发现的入口，包括 `pages` 下的页面、API 路由、`_app`、`_document`、配置模块、全局样式、公共元数据和声明文件。

候选项只有通过全部适用检查后才能删除：

1. 检查直接导入、相对路径导入、别名导入、重新导出、动态导入、`require`、字符串引用和配置引用。
2. 跟踪统一导出文件和本地包装模块，判断候选项是否存在间接消费者。
3. 检查框架约定、运行时发现、脚本、CSS 引用、公共 URL 和文档记录的运维用途。
4. 确认删除不会改变活跃模块所依赖的公共导出接口。
5. 修改后执行与风险相匹配的验证。

用途不明确的候选项一律保留。仅凭普通导入扫描未发现文件，不足以作为删除依据。

## 清理流程

### 1. 建立基线

记录干净的 Git 状态，并运行现有 TypeScript 检查和自动化测试。在所需外部服务与环境允许时，删除前运行生产构建；如果受环境限制，则记录阻碍，并将通过的本地检查作为基线。

### 2. 建立候选清单

分别建立本地源文件、活跃文件内符号、静态资源和 npm 依赖的候选清单，并分类为：

- **确认未使用：** 所有引用和约定检查均未发现消费者。
- **用途不明确：** 无法排除运行时、框架、外部系统或内容驱动的使用方式。
- **正在使用：** 至少存在一个有效消费者。

只有“确认未使用”的候选项进入实施阶段。

### 3. 最小化修改

删除确认未使用的文件，并从活跃文件中移除确认未使用的代码。保持周边格式和现有架构不变。通过 npm 移除依赖，以确保 `package.json` 与 `package-lock.json` 一致，不升级或改写无关依赖版本。

### 4. 增量验证

先验证源码清理，再验证依赖清理，最后验证组合结果。如果某项删除导致失败，则恢复该候选项，并将其标记为“正在使用”或“用途不明确”，不通过调整无关代码来迁就删除。

## 验证

最终修改必须通过：

- `npx tsc --noEmit`
- `npm run test:performance-fixes`
- `npm run build`；只有可明确记录的外部服务或环境失败可以例外

最终复核还覆盖以下路由和功能入口：

- 首页和次级落地页
- 规范 Article 路由和旧版 Article 路由
- 分类与标签路由
- Notion 内容渲染
- 简历工具
- 邮件订阅、评论、广告、分析、翻译和统计集成
- Sitemap、robots、图片代理和其他 API 路由

## 交付内容

实施报告将列出：

- 删除和修改的文件
- 移除的依赖
- 保持不变的行为
- 验证命令和结果
- 因用途不明确而有意保留的候选项
- 剩余风险或受环境限制的检查

本次清理不创建分支，不提交、不推送、不合并，也不部署。
